1 · Summary

The plan in brief

Written against the system as built, from the Sprint 5 architecture workshop on 28 October, not against the Confluence ruling pages. Where the two differ, this plan follows the build and lists the gap. The existing Agent Validation Test Plan supplies the method. This document scopes that method to what exists and adds the standards, goals and work plan.

NoneModel gateway or content-safety control deployed. Agents call models directly
11GLS rule waivers (EX-0001–0011), all expiring 31 Dec 2026, none machine-checked
174Open Dependabot alerts on 28 Oct. Code and secret scanning disabled
4–8 wksPen-test lead time, plus 10 business days to the report

What this plan decides

  1. Eleven test types, each tied to a named standard and a measurable goal (§4).
  2. Internal standards are the floor and win wherever they exist. Public standards define "good" only where the internal ones are silent (§3).
  3. Numbers are checked exactly, never judged. Every figure on screen, in narrative and in the deck must match a calculation output.
  4. Build on what SN already has; do not rebuild it. SN has a governance checker, service test suites, contract validation, per-agent tests and eval contracts, and adversarial review passes (§2). SN keeps those. An in-house testing engineer adds the independent layer: the golden eval set, a held-out set, the guardrail suite, acceptance journeys and the release evidence.
  5. Three actions cannot wait for the engineer: send the pen-test questionnaire, classify OpCat's data, and book BCN analyst time.

TT-01UI journeys and accessibilityReact SPA · CopilotKit / AG-UI chat panel · case stream and agent stream over SSE

What we test

  • Critical journeys: target set-up, peer discovery, edit and confirm, Case for Change, analysis drill-down to evidence, a chat-driven edit, export.
  • Gates as product logic: a private company with no financials hits a hard gate and blocks; low-confidence data hits a soft gate, which proceeds and flags. A hard gate downgraded to a warning is a P0 defect.
  • Every figure on screen links to a source that resolves.
  • Stream behaviour: resume by last event ID; 429 on a fourth stream; expired cursor after 72 h; access removed mid-stream ends the stream within 60 s.

How

  • Playwright against staging on the GLS data set, in two modes. Replayed: a fixture-owned mock SSE server replays recorded AG-UI and case-stream events. Playwright's route.fulfill cannot stream, so it can't be used for this. Live: a small smoke suite asserting outcomes only.
  • @axe-core/playwright on every route, plus a documented manual keyboard and screen-reader pass (ARC AD-07 asks for frequency and method).
  • AG Grid needs a real browser: jsdom has no layout. Charts are snapshotted as server-rendered SVG.

Goal and pass criteria

  • 100% of critical journeys pass, each with audit-actor and provenance assertions.
  • 0 WCAG 2.2 AA violations on any route.
  • First partial result within 30 s of run start (Technology Choices §9.5).

Already built, and gaps

Built: frontend contract and network-boundary tests (Sprint 3); OI3-227 QA on the peer selection screen. Not seen: end-to-end or accessibility automation. The 4 October dev checks found UI handling of the 429 untested, a silent start before the first progress step, and answers arriving as a single block. Each becomes a test case.

  • WCAG 2.2 · Playwright accessibility testing · Playwright mocking · AG Grid testing
  • Internal: Dev streaming and chat-agent checks · Vision (hard and soft gates)
TT-02Component and contractUI components · TypeScript BFF · Python services · contracts/ JSON Schemas

What we test

  • Component behaviour, state transitions and tool-call handling in the UI.
  • BFF and service domain logic in isolation.
  • The four contract families (audit-events, case-stream, search-artifact, agents), which are checked at CI, test, build and runtime.
  • REST implementation against its OpenAPI schema, including cases nobody wrote a test for.
  • Access-control scenarios in unit and integration tests (ARC AD-22).

How

  • Vitest with Testing Library and MSW sse() for the UI and the BFF; pytest for Python services.
  • Schemathesis against each service's OpenAPI.
  • Integration tests on Testcontainers Postgres, the deployed substrate, not SQL Server as the original plan says.

Goal and pass criteria

  • ≥80% coverage on new deterministic code; static analysis with no high or critical findings; ≥2 reviewers. This is the AIS definition of done.
  • 100% of contract schemas validated at all four points.

Already built, and gaps

Built: the governance checker (25 checks, clean on 17 Sep); service suites in pytest and on the BFF's own test runner; JSON Schema contracts validated at four points. Gaps: agent contracts (budget, eval, tool-catalog and others) are checked at runtime only for file existence, which SN called "the gap we need to fulfil". Coverage thresholds and reviewer counts are not known; WP-01 finds out.

  • MSW sse() · Schemathesis · Sonar way
  • Internal: AIS "Well Operated" build guide · ARC assessment tracker
TT-03Deterministic calculationCalculation engine · the GLS port of calc.py inside the BFF · cost-bar recalculation after a peer change

What we test

  • Golden fixtures: the engine reproduces BCN's pre-calculated cost bars, levers and size of prize exactly.
  • Parity: while waiver EX-0002 stands, the BFF port and calc.py must agree on every fixture. Two implementations of one formula diverge silently otherwise.
  • Recalculation (S4-12): a peer missing a metric is excluded, and the exclusion is visible to the user.
  • Properties: unit and currency invariants, determinism, cycle rejection.
  • Trace replay, once completed cases exist.

How

  • pytest with pinned BCN fixtures; exact equality, never an approximate match.
  • Hypothesis for the Python engine and fast-check for the TypeScript port.
  • Fixtures are versioned and hashed; the data set itself stays outside git, as it does today.

Goal and pass criteria

  • 0 mismatches against BCN outputs; 0 parity differences. Any mismatch is a defect, never "model variation".
  • ~90% branch coverage on the engine, the upper end of the AIS range, because this is the one place exhaustive testing is possible.

Already built, and gaps

Built: engine unit tests (test_adjustments.py, test_ports.py); the grammar has no dynamic execution, verified on 17 Sep. The BFF port is tested against BCN reference outputs. Parity with services/calculation-engine/ is not known to be tested, and the engine itself is untouched by GLS. Re-check 17 Sep findings B1 (a failed reconciliation does not lower confidence, and is untested) and S1 (the MCP path bypasses the calculation port).

  • ISO/IEC/IEEE 29119-4 (equivalence, boundary, decision-table techniques)
  • Internal: Technology Choices §9.2 · Agent Validation Test Plan §7.5
TT-04Data and company searchData product (bronze → silver → gold) · company-search-service · entity normaliser · golden-data coverage

What we test

  • A known-answer suite for company search: ticker, fuzzy match, BM25 and trigram. It includes a company absent from the snapshot, where the top score still normalises to 1.000.
  • Entity normalisation and transliteration, for example "The Coca-Cola Company" → "coca-cola" and "Nestlé" → "nestle".
  • Search artefact integrity: version, snapshot ID, per-segment SHA-256.
  • Golden-data coverage (S4-02): all ~100 companies, with gaps flagged so they cannot become peers.

How

  • pytest with exact assertions; the deterministic side uses no model and no network.
  • A coverage report by company and metric, generated on every data load.

Goal and pass criteria

  • Known-answer suite at 100%; artefact fingerprints verify on load.
  • No company with incomplete data can be proposed as a peer.

Already built, and gaps

Built: the normaliser carries a version and a fingerprint, and has a known-answer demo across six rule families; search artefacts carry per-segment SHA-256 fingerprints; company-search sizing is measured and budgeted. Gaps: the alias index has 0 rows, so a company cannot be found by another name. Parent and subsidiary use is undecided. Both are business questions, for Stephanie and Noah, that the suite's expected answers depend on.

TT-05GenAI content evaluationpeer-discovery · chat-assistant · gls-narrative · deck-planner · deck-writer (Foundry Agent Service, Sweden Central)

Built: per-agent unit tests under agents/, and an eval.contract.json per agent, which is declared but not yet enforced at runtime. Not built: statistical evals over repeated trials, a golden eval set or a held-out set. The harness should read SN's eval contract rather than introduce a second format.

A black-box harness drives each agent through the same BFF endpoints the UI uses, with a test identity. It records full trajectories and tags every result with an agent version manifest: prompt hash, tool-catalog version, model deployment and Foundry agent version. Without the manifest, a regression cannot be traced to a change.

Graders, cheapest first

  1. Code graders: structural invariants (every claim has evidence, every figure has a trace); right tool with the right arguments; end state as expected. Binary.
  2. Numeric reconciliation: every number must match a calculation output for that request. An unmatched number counts as re-derived, which breaks the single-calculation-authority rule, and fails.
  3. LLM judges, for prose only: groundedness, faithfulness, task adherence. Binary rubrics, one judge per dimension, with "unknown" allowed. A judge may gate only after calibration against SME labels (TT-11).

Goal and pass criteria

  • Invariants pass in every trial (pass^k): k=3 in the smoke eval, k=5 nightly.
  • Quality metrics stay at or above the approved baseline, judged by a paired confidence interval on the same task set. v0 thresholds are relative to the baseline; absolute targets are set after the first SME-calibrated round.
  • Agent-affecting changes pass the smoke eval before merge (CQ-AI-PMT-02). Model or provider changes pass the full set plus the held-out set before the switch.

Golden eval set v0

Seeded from the 10 GLS targets. SN's own plan is for the golden data set to become the evaluation set after GLS, which is sound. Contents:

  • reference peer sets;
  • expected opportunity themes;
  • known-good claims;
  • 20–50 chat tasks drawn from real failures found in error analysis;
  • negatives: subsidiary confusion, a company absent from the snapshot, ambiguous names, a private company, sectors with poor disclosure.

The set is split into a dev set SN may see and a held-out set it may not.

TT-06Guardrails and AI securityPrompt injection (direct and indirect) · tool misuse · chat writes · web data · exfiltration

What we test

  • Every control in the guardrail register (§5) has at least one test proving it blocks what it should.
  • An injection corpus built around the two shapes the architecture names, uploaded documents and retrieved web pages, plus tool responses carrying instructions:
    • white text in a PDF;
    • PPT speaker notes;
    • Excel comments.
  • Agent-specific failure modes (CQ-AI-AGT-03): goal hijacking, scope creep across steps, unintended side effects from chained tool calls.
  • Web data is verified by a person before use. This is the architect's stated rule, even for whitelisted URLs.

How

  • PyRIT's cross-domain injection (XPIA) workflow, or the Foundry AI Red Teaming Agent, which wraps it. Both are preview; keep them in their own environment.
  • promptfoo red-team plugins as an alternative. It is now owned by OpenAI, so weigh neutrality.
  • Each case asserts outcomes, not wording: no forbidden tool call, no agent write in the audit trail, no claimed change.

Goal and pass criteria

  • 100% of named threat classes covered (OWASP LLM01, LLM02, LLM06, LLM08, LLM09; Agentic ASI01, ASI02).
  • No unresolved high or critical finding at release; every control has a passing test.

Built: SN's adversarial review passes, a whole-repo security review procedure, control-coverage.json, and a delegation contract limiting writes to reversible actions in the user's turn. Known gap: the injection control does not exist yet. Technology Choices names Content Safety at the gateway as the control; no gateway is deployed. Until Portkey and Content Safety are built, this suite measures what gets through rather than proving a control. Findings are expected and should be logged as security findings, not test failures.

TT-07Application securitySAST · SCA · secrets · DAST · ASVS L2 test pass · third-party penetration test

What we test

  • Static analysis on every PR; dependency scanning before merge to a production branch; DAST before any production release (TSG Application Security).
  • ASVS 5.0 Level 2 requirements as test cases, cited as v5.0.0-x.y.z. Access control and data protection are raised to L3 where case isolation needs it.
  • Exposure checks: no client names in URLs, file names or error responses (ARC SD-22).

How

  • GitHub Advanced Security (CodeQL, secret scanning), which is licensed.
  • SCA tool to be ruled on by TSG: Snyk Open Source, which TSG names, or Dependabot.
  • OWASP ZAP against staging nightly, plus a blocking run at pre-release.
  • The pen test is booked through SecRisk.

Goal and pass criteria

  • No critical vulnerability enters production (SDLC Guidance).
  • Remediation within 10, 30, 90 and 180 days for Critical, High, Medium and Low; 48 h for Wiz critical and high findings on public endpoints.
  • A third-party pen test before production; semi-annual if OpCat is classed Confidential or above.

Already built, and gaps

Built: Dependabot; image scanning before push; secret canaries in the governance checker; an on-demand security scan framework. Gaps: code scanning, secret scanning, code quality and the security policy are all disabled, with 174 open Dependabot alerts.

The dev posture has the WAF in detection mode, a Postgres "public with selected IP" commit, Service Bus with no private endpoint, a plaintext Redis container, and CI secrets in GitHub rather than a vault.

TT-08Audit and provenanceaudit-service hash chain · actor attribution · evidence-service claim lineage

What we test

  • Every auditable action records actor.kind (human, agent or service) correctly. An agent acting for a user is recorded as the agent, on behalf of the user.
  • The hash chain verifies end to end, and digests match WORM storage.
  • The outbox commits a write and its audit record together, or neither.
  • Every rendered claim drills down to raw evidence in one traversal.

How

  • An audit assertion in every TT-01 journey that causes an auditable action.
  • A chain-verification job over staging, nightly.
  • Fault injection between the write and the outbox.

Goal and pass criteria

  • 100% of critical actions carry the right actor and initiating user; 0 chain breaks; 0 orphan claims.

Already built, and gaps

Built: audit-service tested (Sprint 3). Append failures are abandoned for redelivery, never swallowed, and the outbox relay bounds its retries (17 Sep). Gaps: in GLS mode the BFF bypasses the hash-chained audit trail (waiver EX-0006). The chain itself is hand-rolled (repo ADR-0021), against ADR-009's ledger tables, so it needs proving rather than assuming.

TT-11Human review and acceptanceBCN for methodology, partners for usefulness · judge calibration

What we test

  • Whether the output is any good, on a held-out sample. Nothing automated answers this.
  • Binary rubric checks:
    • correctness;
    • completeness;
    • defensibility ("could I say this to a CEO?");
    • transparency ("can I see why?").

Goal and pass criteria

Conventions

  • IDs: each test ID is prefixed by its test type, for example TT05-PD-0007.
  • Traceability: each case declares standard_refs, which point to an internal requirement row or a public standard clause.
  • Assert outcomes, never model wording. Product copy is the only exact text asserted.
  • Test data: no production documents in test, ever. Synthetic companies for functional tests; the pinned GLS set for evals, once its permitted use is cleared; recorded source responses for integration.
  • No secrets in the repository. Test identities and keys come from a vault at run time.
  • Every run is tagged with the agent version manifest and the dataset version.
  • One format per thing: eval cases follow SN's eval.contract.json where it fits, and repository-level rules live in SN's governance checker. Don't fork either.

Grader: numeric reconciliation evals/graders/reconcile.py 
"""Every number shown must equal a value the calculation returned for this request."""
import re
from decimal import Decimal

NUMBER = re.compile(r"[-+]?\d[\d,]*(?:\.\d+)?\s?%?")

def unmatched_figures(surface_text: str, calc_values: list[Decimal], places: int = 1) -> list[str]:
    """Return figures in surface_text that match no calculation output. Pass = empty list."""
    allowed = {round(v, places) for v in calc_values}
    misses = []
    for raw in NUMBER.findall(surface_text):
        value = Decimal(raw.replace(",", "").replace("%", "").strip())
        if round(value, places) not in allowed:
            misses.append(raw)
    return misses

Runner: pass^k and paired comparison evals/runners/stats.py 
def pass_hat_k(trials: list[bool]) -> bool:
    """P0 invariants: every trial must pass."""
    return all(trials)

def paired_delta(candidate: list[float], baseline: list[float]) -> tuple[float, float]:
    """Mean per-task difference and 95% CI half-width, on the same task set."""
    diffs = [c - b for c, b in zip(candidate, baseline, strict=True)]
    n = len(diffs)
    mean = sum(diffs) / n
    var = sum((d - mean) ** 2 for d in diffs) / (n - 1)
    return mean, 1.96 * (var / n) ** 0.5

def regressed(candidate, baseline, max_drop: float) -> bool:
    mean, half = paired_delta(candidate, baseline)
    return mean + half < -max_drop          # the whole interval sits below the tolerance
