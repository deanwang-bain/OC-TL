1 · What we're aiming for

Four outcomes

01

The numbers are right and traceable

Every figure a partner sees, on screen, in the narrative and in the deck, matches the calculation and drills back to its source.

02

The agents are consistently good

Peer discovery, chat, narrative and the deck agents meet an agreed quality bar across repeated runs, not just once.

03

The product is safe to use

Agents stay within their permissions. Instructions hidden in documents or web pages don't take control. Data stays in its case.

04

Releases are decided on evidence

A short, repeatable set of checks tells us whether a build is ready, and the decision is written down.

2 · How we'd like to approach it

Seven principles

  1. Build on what's already there. The repository already has a lot: the governance checker, service test suites, contract validation, agent tests and eval contracts. We'd rather extend these than start something parallel.

  2. Two kinds of tests. Services, calculation and data get exact checks, so a mismatch is a bug. Agent output varies by design, so we measure it instead: invariants, scores against reference examples, and repeated runs.

  3. Numbers are checked exactly; words are judged carefully. We compare figures with the calculation output; a model never scores them. Model-based judging is for prose, and only once we've checked the judge against people.

  4. Test outcomes, not wording. A test passes because the screen, the data and the audit trail are right, not because an agent used particular words.

  5. Risk first. Start where a mistake would hurt a partner most: the figures, the deck, the actions agents take, and data reaching the wrong place.

  6. Keep it in the repository, easy to hand over. Tests live with the code, run in CI and are documented, so anyone can pick them up.

  7. An independent check on AI quality. BCN curates and holds a set of reference examples. They are used to check releases, alongside the tests the team runs day to day.

4 · Rough shape over time

Now, before rollout, after

Now

Sprint 5
  • Agree the approach
  • Take stock of what exists, and what actually blocks a merge
  • Agree the few things that must be true for the rollout

Before rollout

Sprints 6–7
  • A small reference set per agent, and a quick eval on agent changes
  • Number checks on the narrative and the deck
  • A few key journeys, end to end
  • A first look at prompt-injection risk
  • A simple release checklist

After rollout

December onward
  • Broader eval sets and model-based judging, once calibrated
  • Red teaming, load and resilience testing
  • Tests that track retiring the GLS exceptions by 31 December
5 · Standards we'd like to align to

Reference points, not paperwork

Required

  • The architecture review requirements: ARC v2 and AI Architecture Requirements v2.1, on the Architecture Assessment Tracker
  • TSG security standards: static and dependency scans on PRs, a dynamic scan before release
  • WCAG 2.2 AA for accessibility

Reference

  • The Agent Validation Test Plan for the method, which is already in Confluence
  • OWASP Top 10 for LLM Applications and OWASP ASVS for security
  • ISO/IEC 29119 for how we document test plans and results
