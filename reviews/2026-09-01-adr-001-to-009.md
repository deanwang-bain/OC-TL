# Review: ADR-001 to ADR-009

The set is marked **"Accepted, pending Bain architect review"**, dated 2026-08-21. This
review supports that gate.

## Scope

All nine records: decomposition, calculation engine, adjustment, assistant state, agent
tools, content model, evidence, orchestration substrate, persistence topology. Reviewed
against the product constraints in `context/oi30-brief.md` and cross-checked against
[Technology Choices](https://bainco.atlassian.net/wiki/spaces/OI30/pages/19751338017),
[Architecture Layers](https://bainco.atlassian.net/wiki/spaces/OI30/pages/19705004106),
[Domain Architecture](https://bainco.atlassian.net/wiki/spaces/OI30/pages/19705004114) and
the [Agent Validation Test Plan](https://bainco.atlassian.net/wiki/spaces/OI30/pages/19765133323).

Not reviewed: the capability model and business-layer rulings A1–A7, which sit in the
companion `oi3-capability-derivation.md` and are not in the mirror.

## Outcome

**Approve with comments.** The reasoning quality is high and unusually honest — every
record names rejected alternatives with reasons, ADR-008 cites retirement dates with
sources, and ADR-009 corrects an earlier terminology conflation rather than inheriting
it. None of the nine decisions looks wrong.

Two findings are structural and should be resolved before the set is treated as final.
The rest are gaps to close rather than decisions to reverse.

## Blocking

### B1. No ownership rule for the shared operational store

ADR-001 decomposes by capability domain. ADR-009 puts *case, stage, lineage, grants, peer
sets, angles, opportunities, claims, evidence bindings, content nodes, deck composition
and run status* into **one Azure SQL database**, separated by access pattern rather than
by domain.

Those objects belong to different services. Claims and evidence bindings are ADR-007's.
Content nodes and deck composition are ADR-006's. Peer sets belong to another domain
again. Nothing in the set says who may write which tables.

If every domain service writes directly to the shared schema, the service boundaries are
notional: a schema change ripples across services, and the ADR-006 and ADR-007 ownership
guarantees hold by convention rather than by construction. That is the distributed
monolith failure, and it is much cheaper to prevent now than to unpick.

ADR-001 anticipates the question and answers it only for reads — *"data affinity is
handled through the data foundation rather than through service boundaries"* — which
does not address who owns a write.

**Ask:** state the rule. Either one service owns each table group and others reach it by
API, or the shared schema is deliberate and the boundary is enforced elsewhere. Either
is defensible; the silence is not.

### B2. ADR-009 contradicts itself on chat turns

The Context lists **chat turns** among the roughly nineteen objects requiring
*"transactional read-write on a user-facing read path"*. The decision table then assigns
*"chat thread state"* to **Azure Cache for Redis**, described as *"Ephemeral"* with
*"No durable state."*

Open item 7 circles this — *"durability requirement for assistant sessions beyond
cache-backed restart survival, if any"* — but frames it as an unknown rather than as a
contradiction already inside the record.

It matters beyond tidiness. Under ADR-004 the assistant's state is client-written and the
run payload is ~200KB; if chat turns are not durable, a lost cache is a lost audit trail
of what the assistant was asked. The audit store records actor-attributed *actions*, not
conversation.

**Ask:** decide whether chat turns are operational or ephemeral, and make the Context and
the decision table agree.

## Should fix

### S1. Two accepted ADRs are provisional on one Bain-owned unknown

ADR-009 is *"Accepted. Product selections are provisional pending confirmation of network
isolation requirements."* ADR-008 carries the same dependency, noting some Agent Framework
features *"do not yet fully support network isolation"*. Open item 2 is **Bain-owned**.

So the persistence topology and the orchestration substrate — the two largest decisions in
the set — both hang on one question that StatusNeo cannot answer. Technology Choices §13
independently calls Foundry network isolation *"the largest unresolved item in the set."*

With GLS in mid-to-late October this is a schedule risk, not just an open item. It also
determines private endpoint configuration across all six stores, so it gets more expensive
to answer the longer services are built against an assumed posture.

**Ask:** name an owner and a date. This is the highest-leverage item in the set.

### S2. ADR-007 depends on a latency budget that does not exist

ADR-007 states *"The service is on the read path of the interface, so its latency budget
is user-facing."* There is no latency budget: the
[NFR page](https://bainco.atlassian.net/wiki/spaces/OI30/pages/19704905798) is empty, and
WCAG 2.2 AA is the only hard non-functional target written anywhere.

ADR-002 makes a related claim — engine call latency is *"negligible against the research
and model calls that dominate"* — which is plausible and currently unmeasured.

The 30-minute end-to-end target gets its first public test at GLS. An accepted decision
resting on an unwritten budget is exactly the kind of thing that surfaces in a demo.

**Ask:** put a number on the evidence-service read path, even a provisional one.

### S3. Model-authored adjustment nodes are traceable but not gated

ADR-003 is elegant: adjustment becomes a node type, so trace, override propagation and
blast radius all follow from mechanisms that already exist. The three authorities collapse
into one `authored_by` attribute. This is the best design idea in the set.

But `authored_by` makes a model-authored adjustment **visible**, not **gated**. The
product principle is that the partner retains judgment, with hard gates blocking on
critical input and soft gates flagging lower confidence. An adjustment authored at run
time by a model changes a number the partner will defend to a CEO.

Technology Choices argues the closed grammar reduces validation *"down to a schema check
rather than a security review"*. That is right about safety and insufficient about
correctness: a schema-valid node can still produce a wrong number. Open item 4 assigns the
validation boundary to StatusNeo but scopes it as validation, not as gating.

**Ask:** confirm whether a model-authored adjustment is a soft gate. If it is, that is a
product requirement ADR-003 should reference.

### S4. ADR-004 does not account for collaboration

The client-writes-state decision is well argued, and the failure mode it avoids —
*"silent and plausible"* — is the right one to design against for a tool facing client
executives.

But it assumes one browser holds the truth. ADR-009 persists **collaborator grants**, and
Domain Architecture includes a **Research & Collaboration** domain. Two people on one case,
each with their own client-written state, is not addressed.

**Ask:** state what happens when a case has two concurrent viewers — even if the answer is
that MVP is single-user and collaboration is post-MVP.

### S5. ADR-002 does not name the protocol, and that is where the contradiction lands

ADR-002 requires the engine to be a service *"with a defined API"* but does not name the
protocol. Technology Choices specifies **gRPC with protobuf** for the calculation hop; the
Agent Validation Test Plan specifies **plain REST over HTTP** and excludes gRPC, protobuf
and buf from MVP.

The ADR is not at fault — but it is the right place to settle it, since it owns the
boundary.

**Ask:** name the MVP protocol in ADR-002 and let the downstream pages follow.

### S6. Evidence service must enforce licensing rules that are not written down

ADR-007 states that *"source licensing rules, notably persistence restrictions on analyst
report content, are enforced in one place."* Analyst reports come from LSEG, and the
[LSEG page](https://bainco.atlassian.net/wiki/spaces/OI30/pages/19618889872) is **empty** —
the only data source with no integration notes.

A service cannot enforce a rule nobody has written.

**Ask:** document the LSEG persistence restrictions before the evidence service is built.

## Nits

- **N1.** ADR-008 presents Agent Framework, Durable Functions and Logic Apps as one
  decision without phase tags. Technology Choices §4 marks Durable Functions and Logic
  Apps **north star only**. Add phase tags to ADR-008 so it is not read as three MVP
  substrates.
- **N2.** ADR-001's traceability test — *"a service with no capability trace is removed"* —
  is a good rule with no stated owner or checkpoint. Worth naming when it is applied.
- **N3.** ADR-005's enumerated tool set is described as supporting security review. Once
  the Security Design page exists, it should reference that enumeration explicitly.

## What the set does not cover

Scope is stated as application decomposition, orchestration and persistence, so these are
observations rather than omissions — but each is an area with an empty Confluence page and
no ADR, meaning there is no written standard anywhere:

- Security design and the app-level versus infra-level RACI, which currently exists only
  as a colour band in the technical architecture SVG
- API contract standards (Endpoints & Interfaces Design)
- Observability, beyond ADR-008's note that Agent Framework emits OpenTelemetry spans
- Deployment and CI/CD topology — partly addressed by `decisions/002` in this workspace
- Repository and deployment-unit topology — addressed by `decisions/001`

## Standards gaps hit

This review rests on judgment rather than written policy for: security posture, latency
and availability targets, observability standards, and API contract standards. All four
pages are empty. See `context/open-questions.md`.

**On ADR-001 and MVP phasing.** ADR-001 is a target-state principle. Eleven domains, each
potentially splitting on the synchronous/asynchronous boundary, implies far more services
than the three to six recommended for MVP in `decisions/001`. The two are compatible —
ADR-001 says how to draw boundaries, not how many to deploy on day one — but nothing says
so. Worth an explicit phasing sentence in ADR-001, particularly with GLS seven weeks out.
